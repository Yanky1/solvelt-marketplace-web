## Theming
Tokens are CSS custom properties in `app/styles/tokens.css` (from the Solvelt portal). Dark values apply under `@media (prefers-color-scheme: dark)` for `:root:not([data-theme='light'])` and for `:root[data-theme='dark']`. Bright images use `filter: brightness(var(--img-dim))`.

## Components
`app/components/ui`: Button, LinkButton, Input/Field (label, hint, error), Select, Checkbox, Card, Badge, Price, RatingStars, Skeleton, EmptyState, Breadcrumb, Pagination, Modal/Drawer, Toast. Shell: Logo, Header (search, nav, account, cart placeholder, mobile drawer), Footer (theme switch), skip link, error/404/403 pages. Auth and account: `AuthPage`, `ErrorSummary`, `FormMessage`, `AccountNav`, `AddressForm`, `CsrfField`. `/styleguide` (noindex) shows them all and is covered by axe in light and dark.

## Status
Done: skeleton, tokens, shell, CI and E2E, BFF auth (sign-up/in/out, verify, forgot/reset, resend), profile, addresses, passkeys, three rounds of review fixes. Catalog pages, SEO helpers, sitemap content and the image resize route moved to the M2 worker (W1-53).

## Review 5 (orchestrator review of auth B + review-3)
| Id | Date | Decision | Why |
|---|---|---|---|
| W1-55 | 2026-11-04 | **Passkey challenges are bound to the browser session.** Issuing options (anonymous sign-in or registration) stores `{cid, kind, exp}` in the sealed session cookie; the submit must present that same challenge id, for that ceremony, before `exp` (the API's timeout capped at 5 min, plus 5 s). The binding is dropped from the cookie after every attempt, successful or not (single use). A newer challenge replaces an older one, so two tabs cannot both have one pending. E2E: a challenge minted in session X is refused in session Y, redeemable once by X, replay refused, a sign-in challenge cannot finish a registration. The API still enforces single use and expiry itself. | A challenge minted in one session could be redeemed from another. |
| W1-56 | 2026-11-04 | **Recent sign-in for sensitive changes (O-11).** The sealed session records `authAt` on every password or passkey sign-in. Removing a passkey needs `authAt` within `REAUTH_WINDOW_SECONDS` (default 600, validated 1..3600); otherwise the user is sent to `/account/confirm?next=...`, where the password is checked by the API (a fresh API session is issued, the old one revoked, `authAt` reset) and they return to the page. Sessions from before this change have no `authAt` and must confirm once. Password change (not built yet) must use `hasRecentAuth` too.
